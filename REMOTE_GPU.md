# Running the U-Net on an NVIDIA GPU (Colab or Kaggle)

This document describes how to train and apply the U-Net of this project on a CUDA GPU on a remote
machine, and how to compare that with a CPU run on the same machine. It does not change the
experiment described in the README, and it makes no claim about speed.

## What runs where

| Stage | Library | Device |
|---|---|---|
| Phantom generation | NumPy | CPU |
| Forward simulation, time reversal | j-Wave / JAX | CPU, always |
| Tikhonov matrices and solves | JAX, SciPy | CPU, always |
| Calibration, PSNR/SSIM, bootstrap | NumPy, scikit-image | CPU |
| U-Net training and inference | PyTorch | CPU, MPS or CUDA (`--device`) |

Only the U-Net moves. The physics defines the data that every method is scored on: running j-Wave
on a GPU would change the floating-point results of the FFT-based solver and therefore the inputs,
the baselines and the targets of the comparison. That would be a different experiment. The remote
workflow sets `JAX_PLATFORMS=cpu` before JAX is imported, installs the CPU build of JAX, and checks
at run time that JAX reports only CPU devices.

The U-Net is also a small part of the workload. The expanded evaluation needs 856 forward
simulations and 2,456 time reversals on CPU, while the network has 481,745 parameters and each
training run is 300 optimiser steps on 40 images. A GPU provides a portable way
to run the network on another machine. Whether it is faster for this workload is something to
measure, not assume.

## Device selection

`scripts/train.py`, `scripts/evaluate_mvp.py`, `scripts/evaluate_noise_sensitivity.py`,
`scripts/expanded_evaluation.py` and `scripts/cuda_smoke.py` accept `--device auto|cpu|mps|cuda`,
resolved by `src/device.py`:

- `cuda` and `mps` mean exactly that device. If it is not available the script stops with an error;
  there is no fallback.
- `auto` picks CUDA, then MPS, then CPU. On Apple Silicon this is MPS, as before.
- `scripts/expanded_evaluation.py` defaults to `cpu`, the published protocol.

Determinism (`configure_determinism`):

- CPU: `torch.use_deterministic_algorithms(True)`, as in the published CPU runs.
- CUDA: the same, plus cuDNN deterministic mode, cuDNN benchmark off, TF32 off and
  `CUBLAS_WORKSPACE_CONFIG=:4096:8`. `torch.manual_seed` seeds the CUDA generators as well. Weights
  are initialised on CPU and the batch order is drawn on CPU, so a CPU run and a CUDA run with the
  same seed start from the same weights and see the same batches.
- MPS: no deterministic mode exists; MPS runs are not repeatable.

Mixed precision, TF32, channels-last memory format and any change to batch size or architecture are
not used.

## Output protection

The committed files in `report/`, the local checkpoints in `experiments/` and the generated data in
`data/` are the evidence behind the published results. The checkpoint
`experiments/unet_checkpoint.pt` was trained on MPS and cannot be regenerated exactly.

- A remote run writes only under `results/<RUN_ID>/` (`data/`, `checkpoints/`, `report/`, `smoke/`,
  `env/`). `results/` is ignored by git.
- With `PHOTOACOUSTIC_PROTECT_HISTORICAL=1` (set by both notebooks), or whenever the device is CUDA,
  a write to `report/`, `data/` or `experiments/` is refused. `--allow-historical-overwrite` on
  `train.py` is the only override.
- Outside those directories an existing file is not replaced unless `--overwrite` is given.
- `scripts/train.py` never replaces an existing checkpoint without `--overwrite`, on any device.
- Local CPU and MPS runs with the default paths behave as before and reproduce the committed
  reports.

## Workflow

Both notebooks are thin launchers around the same repository scripts. They differ only in the
working directory, where results are kept and how the archive is handed over. They are generated by
`scripts/build_remote_notebooks.py` and stored without outputs.

1. Configuration: `REF` (full commit SHA), `RUN_FULL = False`, and one `RUN_ID` per session. The
   `RUN_ID` is written to a file the first time and read back afterwards, so running the
   configuration cell again does not start a new run.
2. GPU and interpreter report (`nvidia-smi`).
3. Clone, check out `REF`, verify that `HEAD` equals `REF` and that the tree is clean.
4. Dependencies (`scripts/remote_setup.py`, see below).
5. `pytest`.
6. CUDA smoke (`scripts/cuda_smoke.py --device cuda`).
7. Validation of the smoke verdict (`scripts/cuda_smoke.py --validate`).
8. Runtime estimate for the full run from the components the smoke measured.
9. Packaging of `results/<RUN_ID>/` into a zip archive.
10. Stop. With `RUN_FULL = False` the notebook prints
    `CUDA SMOKE COMPLETE. No full experiment was run.` (Colab) or
    `KAGGLE CUDA SMOKE COMPLETE. No full experiment was run.` (Kaggle), and the remaining cells do
    nothing.

`REF` must name a commit that contains this workflow. A commit cannot contain its own SHA, so the
value is set in `scripts/build_remote_notebooks.py` after the workflow has been committed, the
notebooks are rebuilt, and the notebooks are committed on their own.

### Google Colab

Open `colab/run_cuda.ipynb`, choose a GPU runtime (Runtime > Change runtime type) and run all cells.
Results are written to `/content/photoacoustic-reconstruction/results/<RUN_ID>/` and the archive to
`/content/`; the notebook offers it as a download.

### Kaggle

Open `kaggle/run_cuda.ipynb`. In the notebook settings choose a GPU accelerator and turn Internet
on (needed to clone the repository and install packages), then run all cells. The GPU model is not
assumed; whatever is assigned is recorded. Results are written to `/kaggle/working/results/<RUN_ID>/`
and the archive to `/kaggle/working/`, which Kaggle keeps as the notebook output.

## Dependencies on the remote machine

`requirements.txt` pins the environment the results were produced in (Python 3.11, macOS). On a
remote GPU machine `scripts/remote_setup.py` does the following:

- `preflight` records Python, PyTorch, CUDA and GPU before anything is installed, and stops if CUDA
  is not available.
- `install` installs every line of `requirements.txt` except `torch`, with pip constrained to the
  PyTorch version already present, so the platform's CUDA build cannot be replaced.
- `verify` checks that PyTorch is unchanged and still sees the GPU, that NumPy, SciPy, scikit-image,
  JAX, jaxlib, jaxdf and j-Wave are at their pinned versions, and that JAX reports CPU devices only.

The one deviation from `requirements.txt` is therefore the PyTorch version, which is recorded in
`results/<RUN_ID>/env/environment.json`. If the pinned packages cannot be installed on the platform's
Python version, `install` fails and reports it. The pins are not relaxed automatically, because the
scientific packages determine the numbers.

## The smoke test

`scripts/cuda_smoke.py` is a verification, not an experiment; none of its numbers is a result.

- 4 phantoms (seeds 900000 to 900003, disjoint from every split), two with 16 sensors and two with
  64, simulated and time-reversed on CPU by the project code. Recordings must be `(297, n, 1)` and
  reconstructions `(64, 64)`.
- The project's U-Net on CUDA: parameters and batch verified to be on the device, 20 Adam steps,
  finite losses and gradients, and a final loss below the initial one.
- Inference on CUDA: output `(4, 1, 64, 64)`, finite, with finite PSNR and SSIM computed on CPU
  arrays.
- The checkpoint is saved, reloaded on CPU, and the CPU output is compared with the CUDA output.
  The tolerance is `1e-4` absolute: rounding differences between CPU and CUDA kernels are several
  orders of magnitude smaller on outputs of order one, and an error of that size corresponds to an
  80 dB PSNR floor, far above any reconstruction here.
- Synchronised timings, peak CUDA allocator memory, and the same 20 steps on the machine's CPU as a
  timing reference.

The verdict is `results/<RUN_ID>/smoke/smoke_verdict.json`. The run is accepted only if every check
passed on a CUDA device; a normal exit is not enough. A local dry run on CPU or MPS
(`--allow-non-cuda`) exercises the same code but is rejected by `--validate` as a CUDA smoke.

## The full experiment (gated)

`scripts/remote_experiment.py` does not start without `--confirm-full`, and the notebooks pass that
flag only when `RUN_FULL = True`. It follows the protocol of `scripts/expanded_evaluation.py`
without changes: the same splits, 400 test images, five noise levels, the same U-Net recipe and
metrics, and training seeds 0 to 4.

- Data: generated once with j-Wave on CPU and shared. The time-reversal reconstructions at every
  noise level are cached, so both arms score identical physics output.
- Arm A: U-Net on CPU, deterministic, seeds 0 to 4.
- Arm B: U-Net on CUDA, deterministic settings, seeds 0 to 4.
- Reports: `report/cpu/` and `report/cuda/` (the expanded evaluation), `report/<arm>/mvp_seed0/`
  (the 8-image evaluation of that arm's seed-0 network) and `report/comparison/`.

Five seeds are used because the published results already vary by about 2 dB between identically
configured training runs. A single network per device could not separate a device effect from that
spread.

The 8-image evaluation in `mvp_seed0/` scores a newly trained network. It is not the original MPS
checkpoint behind `report/mvp_results.txt`, and its results file says so.

The Tikhonov baseline, its diagnostics and the model-mismatch check are not part of this run. They
use only JAX and SciPy on CPU, are independent of the U-Net device, and the noiseless Tikhonov
solve is sensitive to the linear-algebra library. They can be run separately on CPU as optional,
CPU-heavy extensions.

## Comparing CPU and CUDA

`scripts/compare_devices.py` reports, for each noise level, sensor count and metric:

- PSNR and SSIM per network in each arm, with the mean and standard deviation over the five networks;
- the U-Net gain over calibrated time reversal in each arm;
- CUDA minus CPU, per network and for the network average, with a paired bootstrap interval over
  test images;
- where the published mean, its interval and the published between-network range lie.

Three effects are kept apart:

- device (arm B against arm A, same machine, same data);
- platform (arm A against the published CPU results, which were produced on another machine);
- training randomness (the spread between seeds within an arm).

Agreement between devices is statistical. CPU and CUDA use different convolution kernels and
summation orders, training amplifies rounding differences, and the checkpoint is chosen by lowest
validation loss, so a small difference can select a different epoch. Two devices give two sets of
networks in the same way that two seeds do. Bitwise equality is expected only for a rerun on the
same device with the deterministic settings, and for the time-reversal inputs, which are checked to
be identical in both arms.

## Timing and memory

Timings are recorded separately for the forward simulation, time reversal, U-Net training, U-Net
inference and the metrics, with an end-to-end figure for the run.

- CUDA and MPS regions are synchronised before the timer starts and before it stops.
- The first training epoch and the first inference call are reported separately as warm-up.
- For CUDA the peak allocated and peak reserved memory of the PyTorch allocator are recorded. These
  are not process memory and cannot be compared with MPS or host RSS figures.

How to read them:

- Only arm A against arm B on the same machine is a device comparison. A laptop MPS time against a
  remote GPU time is not.
- U-Net time and end-to-end time are different quantities. The physics is the same CPU work in both
  arms, so an end-to-end difference can be much smaller than a U-Net difference.
- The runtime estimate printed by the notebook is an extrapolation from the smoke, not a measurement.

## Checkpoints

A checkpoint is a dictionary with `model_state`, `epoch`, `val_loss` and `seed`. The state
dictionary is moved to CPU before saving, so the file carries no device tag and loads on CPU, MPS or
CUDA. Every loader also passes `map_location` and `weights_only=True`. Checkpoints written before
this change load unchanged. A `.meta.json` file beside each remote checkpoint records the commit,
devices, library versions, seed, model and training configuration, dataset fingerprint, timing and
CUDA memory.

## Known risks

- The pinned packages may not install on the Python version of the remote platform. The workflow
  stops in that case.
- A GPU build of JAX that the platform preinstalled may remain installed next to the pinned CPU
  JAX. It is not used (`JAX_PLATFORMS=cpu`, verified), and its presence is recorded.
- j-Wave on Linux x86 may not reproduce the macOS arm64 data bit for bit. This is the platform
  effect above and is independent of CUDA.
- The CUDA path has been exercised only through its CPU and MPS equivalents and with mocked CUDA
  calls until the smoke has been run on a GPU.
- Kaggle sessions without Internet access cannot clone or install.
